# Dark Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add System, Light, and Dark appearance to standalone Music Party interfaces and match YouTube Music's theme for embedded controls.

**Architecture:** Share a small dependency-free preference controller, package it locally for each standalone surface, and expose the applied theme on the document root. Use existing semantic theme tokens and keep YouTube Music theme detection separate from popup preferences.

**Tech Stack:** JavaScript, TypeScript, CSS, React, Vite, daisyUI, HeroUI, Cloudflare Workers, Node test runner, Vitest.

**Spec:** [Dark mode across Music Party](../specs/2026-11-25-dark-mode-design.md)

## Global Constraints

- Default to **System**. Follow live device appearance changes in System mode; ignore those changes while explicitly set to Light or Dark. Apply changes immediately without reloading.
- Store only the preference in browser-local storage. No cross-origin or cross-device sync, new extension permission, or backend change to room state.
- Keep existing layouts and branding; do not tint album art, screenshots, logos, or QR codes.
- Embedded controls match the host page and never recolor YouTube Music itself. Telegram is unchanged.
- Leave the unrelated requester-display work and untracked browser artifacts untouched. No deployment.

## Review Focus

- Blocked storage: explicit choices still work for the current page.
- Invalid storage: start in System rather than accepting arbitrary theme values.
- OS changes with an explicit override: theme remains fixed until System is selected again.
- Regenerated legal pages and Worker fallback: appearance is available even on pages that bypass normal static hand-authored headers.
- Embedded controls after a host theme change: both sidebar and an already-open dialog update without changing popup preferences.

### 1. Shared controller

**Files:** `scripts/appearance.js`, `scripts/appearance.test.mjs`, `scripts/sync-appearance.mjs`; generated `appearance.js` in each app's `public/` directory.

**Interface:** A classic script runs at load, reads `data-appearance-key` and optional `data-light-theme`/`data-dark-theme` from its script element, sets `document.documentElement.dataset.theme`, and binds a select marked `data-appearance-select`. Allowed stored values are `system`, `light`, and `dark`.

1. Write a Node test using `vm` to run the installed script with a fake DOM, media query, and storage. Assert the initial theme is dark on dark system preference, a light override survives reload, a media change under override leaves the theme light, selecting System applies the active media value, invalid storage behaves as System, and throwing storage does not break switching.
2. Run `node --test scripts/appearance.test.mjs`; expect failure because the controller is missing.
3. Implement the controller. Use a head script for early root application and delegated change handling plus a DOM-ready initialization for the picker. Implement `node scripts/sync-appearance.mjs` to copy the source to the four app public paths and `--check` to report drift without modifying files.
4. Verify the Node test and `node scripts/sync-appearance.mjs --check` pass.
