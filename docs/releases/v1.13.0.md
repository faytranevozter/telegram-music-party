# v1.13.0

## New
- Configurable search catalog region and content language: `YT_MUSIC_LOCATION` (ISO 3166-1 alpha-2, default `ID`) and `YT_MUSIC_LANG` (default `en`). Playback availability still follows the connected player's own account region.
- The player now reports tracks it refuses: after `music/get_queue`, the extension confirms the track reached the player queue and reports `queue-unavailable` when the player refused it (region lock, premium-only). The backend removes it from the room queue and warns the chat instead of retrying it forever.

## Fixed
- Play Next keeps the room queue in step with the YouTube Music player: only the current track and what follows it count as queued (history and the automix preview no longer make Play Next a silent no-op), the `ADD_ITEMS` index falls back to the store's `selectedItemIndex` instead of appending to the tail, and the room queue drops the track that the next start replaced so skipped requests no longer linger.
- Inline search no longer reports false video-search errors outside a room and enforces the room's `allowVideoSearch` setting at callback time.
- The Add to Queue callback toast no longer claims the song went to Play Next.

## Distribution
- No new extension permissions, host permissions, or remote services.
- Intended extension archive: `yt-music-party-extension-v1.13.0.zip`.
- Intended backend image tags after release automation: `ghcr.io/faytranevozter/telegram-music-party:1.13.0`, `:latest`, `:1.13.0-sqlite`, `:sqlite`.
- Chrome Web Store review and public availability remain separate from GitHub release publication.

## Release gates
- Smoke-test the built extension against a real YouTube Music tab and Telegram room before distributing it; automated popup tests do not replace end-to-end acceptance.
- Production deploy pins the approved image digest, keeps the existing SQLite volume, environment, port mapping (`127.0.0.1:3010`) and proxy configuration, recreates only the backend, then verifies the running digest, health and bounded logs.
- No Prisma schema change is included; startup migrations should find nothing to apply.
- Pushing `v1.13.0` triggers GitHub release creation, both backend image variants, and Chrome Web Store submission. Pushing `main` separately triggers CI and, when landing-page files change, the Cloudflare deployment.
